# 学习与作答协议

> 这份文件是我在这个知识库里工作的行为准则。接到文件、研究外部资料、给出答案，都按这里走。
> 它同时是「怎么用这个库」的说明书和「答案质量」的验收标准。

## 0. 触发条件

- 你甩来文件、链接、截图或一段材料；
- 你问「这个怎么实现 / 为什么这样 / 哪个方案更好」；
- 我自己判断某个结论需要外部证据才能站得住。

## 1. 接到文件后的五步

| 步骤 | 动作 | 命令 |
| --- | --- | --- |
| 1 入库 | 文件落到 `kb/<分类>/`，建立索引 | 上传，或 `POST /api/reindex` |
| 2 摸结构 | 先看骨架再读正文：标题树、切片、关键词、代码块统计 | `python scripts\kb.py digest <id>` |
| 3 精读 | 按切片读正文，把不确定的数字/术语标记为待验证 | `python scripts\kb.py show <id> --chars 4000` |
| 4 验证 | 关键结论找第二来源；与原文冲突时记入「分歧」 | `web_search` / `web_fetch` |
| 5 沉淀 | 写笔记并回链原文，追加学习日志 | `kb.py note …` + `kb.py log …` |

不跳过第 2 步。长文档全文硬读会漏结构，先看骨架能判断哪几节真正相关。

## 2. 外部检索规则

- **来源分级**：A = 官方文档 / 源码 / 规范；B = 维护良好的工程博客、教材；C = 论坛、问答、二手转述。C 级只当线索，不能当结论。
- **交叉验证**：事实性结论至少两个独立来源；只有一个时标注「单一来源，待验证」。
- **时效标注**：涉及版本或 API 的，写明版本号与检索日期；旧结论要给出适用边界。
- **实测优先**：能跑的一律本地验证；不能跑的要明确写「未验证」。
- **区分口径**：引用里写清是「文档如此说」还是「我实测如此」。

## 3. 笔记格式

```markdown
# <主题>

## 结论
三行以内，直接给答案。

## 机制
因果链，不堆术语。

## 实现
代码 / 命令 / 参数，带占位符。

## 边界与失败模式
什么情况下会坏，坏成什么样。

## 在本项目里的落点
改不改、成本、风险、回滚方式。

## 验证记录
跑了什么，输出什么。

## 来源
[标题](URL) · 版本 · 访问日期
```

没跑过的东西只写「设计」，不写「实现」。

## 4. 作答结构

1. **结论先行**：一句话 + 关键数字。
2. **为什么**：机制层面的因果。
3. **怎么做**：可复制的命令、代码、步骤。
4. **代价**：复杂度、性能、维护成本、会坏在哪。
5. **怎么验证**：判断它是否真的生效。
6. **参考**：链接与文件路径。

## 5. 自检清单

- [ ] 每个数字都有出处或实测记录
- [ ] 没有把「应该 / 大概」写成事实
- [ ] 代码能跑，或已标注未验证
- [ ] 说明了不适用的场景
- [ ] 结论可被别人复现

## 6. 不做

- 不把推测写成结论；
- 不用「最佳实践」代替具体取舍；
- 不隐藏失败样本与边界条件。
