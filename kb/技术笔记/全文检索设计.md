# 全文检索设计说明

## 目标

不用词嵌入、不用向量库、不用外部搜索引擎，在一台普通机器上做到「上传即可搜、中文能搜准」。

## 为什么不用 LIKE

`LIKE '%关键词%'` 无法使用索引，文档一多就退化成全表扫描；也无法按相关度排序，更无法给出命中片段。SQLite 自带的 FTS5 是倒排索引 + BM25 打分，正好补上这三点。

## 中文怎么办

FTS5 的 `unicode61` 分词器把连续的汉字当成**一个**词元，所以「知识库」只会有这一个 token，搜「知识」永远打不中。

解决办法在写索引时完成：把每个汉字用空格隔开。

```python
def prep(text):
    return CJK_RE.sub(lambda m: f" {m.group(0)} ", text)
```

于是「知识库」被索引成三个 token：`知` `识` `库`。

查询时把用户输入的中文词转成短语：

```
"知 识 库"
```

FTS5 的短语查询要求 token 连续出现，因此等价于一次「按字的短语匹配」。如果没有任何结果，系统自动降级为宽松模式：

```
"知" AND "识" AND "库"
```

两次查询都命中时，用 BM25 排序，再叠加标题 / 路径命中的加分，最后合并到文档级别去重。

## 切片

长文档整篇作为一个检索单元会让 BM25 的长度归一化失真，也无法精确给出命中位置。因此：

1. 先按 Markdown 标题分节；
2. 每节按空行装箱，目标长度约 1100 字符，硬上限 1800；
3. 每个切片单独一行写入 `chunks` 表，同时把 `prep()` 后的文本写入 `chunks_fts`。

`chunks.id` 直接作为 FTS5 的 `rowid`，检索时一次 JOIN 就能拿回原文，用于生成高亮片段。

## 数据与文件分离

- 文件本身永远以原始格式保存在 `kb/` 下，可被任何工具读取、可被 Git 管理。
- `data/kb.sqlite3` 只是投影：删掉它、重建索引即可完整恢复。
- 扫描时用 SHA-256 + mtime 判断是否需要重新索引，内容没变的文件直接跳过。

## 下一步可以做什么

- 词嵌入：在 `chunks` 旁边加一张向量表，检索时做混合排序（BM25 + 余弦相似度）。
- 增量监听：用 `watchdog` 监听 `kb/` 变化，替代手动重建索引。
- 多用户：把 `documents.tags` 换成独立表，加入权限字段。
